Apollo Cache & API Flow

How the inventory-items feed reads, and how create update delete stay live without refetching the list — grounded in the actual commerce-ma / core-server code.

The one idea behind everything: the Apollo cache is a normalized store — every entity is saved once under a key like InventoryItem:abc123, and every list/screen just holds a reference to it. So we never re-download a list; we surgically edit the cache, and every view that points at the same entity updates itself.

① The API structure — one request, five hops

The mobile feed talks GraphQL (not REST). A query/mutation travels down this chain and the response comes back up the same way:

commerce-ma mobile remote
Apollo Client builds the operation & sends HTTP POST {tenantBaseURL}/graphql. authLink attaches the token, x-bu-id, platform; tenant URL comes from Keychain.
▼  HTTPS · GraphQL over POST
core-server GraphQL gateway
InventoryItemsResolver (Apollo driver on Fastify) receives the operation, e.g. inventoryItems(first, after, filters, search, sort).
▼  resolver → gateway service
Gateway service thin forwarder
InventoryItemsGatewayService.findForFeed() reshapes args and forwards over the message bus.
▼  nats.send('commerce', 'inventoryItems.feed', payload) · request/reply
commerce-service NATS microservice
NATS handler → InventoryItemsService.findForFeed() builds the keyset query (FilterProcessor + KeysetProcessor + CursorCodec) → Repository → Postgres.
▲  result travels back up the same chain

Two pagination styles, on purpose

The web table uses offset pagination (inventoryItems.table). The mobile feed uses keyset/cursor (inventoryItems.feed) → returns a Relay connection. Offset drifts when rows are inserted/deleted mid-list; keyset is stable for infinite scroll.

What a "Relay connection" is

{
  edges: [{ cursor, node: {…item} }],
  pageInfo: { hasNextPage, endCursor }
}

Each row carries its own opaque cursor (encoded sort-key values). The next page asks for rows after endCursor.

② How the cache is laid out

The host (core-app/src/host/config/apollo.ts) creates one InMemoryCache; the commerce-ma remote shares it. The cache is a flat key→value map with two kinds of entries:

Normalized entities — saved once, by identity
InventoryItem:abc{ id:"abc", name:"Steel bolt", code:"BOLT-M6", … }
InventoryItem:def{ id:"def", name:"Washer", … }
ROOT_QUERY fields — hold references (→), not copies
inventoryItems({filters,search,sort}){ edges:[{cursor, node:→InventoryItem:abc}, {…→def}], pageInfo }
inventoryItem({id:"abc"})→ (redirected to InventoryItem:abc)

Two typePolicies make this work:

relayStylePagination(['filters','search','sort'])

Teaches the cache to merge pages of the connection automatically. The key args are filters/search/sort — so each filter combo is its own cached connection, while first/after (the page cursor) are excluded. Result: fetchMore appends to the same cached list with no manual merge code.

inventoryItem read redirect

read(_e, {args, toReference}) {
  // point the single-item query at the
  // entity the FEED already cached
  return toReference({
    __typename:'InventoryItem', id: args.id
  });
}

So opening an item's detail reads it straight from cache — no network call.

The fragment trick: the feed query, the single-item query, and create/update mutations all select the same InventoryItemFields fragment. So the object the feed caches is byte-for-byte the object detail/edit need — they all resolve to the one InventoryItem:{id} record. Edit it once → every view updates.

create  Insert without refetch

  1. Submit form → useCreateInventoryItem().mutate({input})
    POST createInventoryItem(input) → resolver → gateway → NATS → DB insert.
  2. Server returns the full new entity (resolver returns result.data, selected via the shared fragment).
  3. Apollo auto-normalizes it → writes a new InventoryItem:newId record into the store.
  4. The hook's update() runs cache.modify on the inventoryItems field → prepends a new edge pointing at the new entity. (dedupes by id; skips if already present)
  5. Every screen reading the feed re-renders with the item on top. No list GET.
connection.edges — before
[ →abc, →def ]
→
after cache.modify
[ →new, →abc, →def ]

update  Edit with zero cache surgery

  1. Submit edit → useUpdateInventoryItem().mutate({id, input})
    POST updateInventoryItem(id, input).
  2. Server updates, then re-fetches & returns the full entity.
    In the resolver: await update(id, input); return findById(id); — the REST/NATS update only returns {success}, so the resolver composes a fresh read so the client gets the whole object back.
  3. Apollo merges it by identity into the existing InventoryItem:{id} — same key, fields overwritten.
  4. List cell + detail update automatically, because both already point at that same record. No cache.modify, no refetch.
InventoryItem:abc — before
{ name:"Steel bolt", code:"BOLT-M6" }
→
after merge
{ name:"Steel bolt v2", code:"BOLT-M6" }

Identity merge is why returning the entity matters — a mutation that returns only {success} would force you to refetch.

delete  Remove from every list at once

  1. Confirm → useDeleteInventoryItem().mutate({id})
    POST deleteInventoryItem(id) → server checks references → DB delete → returns {success}. The client already holds the id it deleted.
  2. Hook's update() drops the edge — cache.modify filters the connection's edges to remove the one whose node id matches.
  3. cache.evict({id:'InventoryItem:'+id}) removes the normalized entity itself.
  4. cache.gc() sweeps up any now-dangling references across all cached queries.
  5. Row disappears from every cached list. The detail screen's inventoryItem(id) redirect now points at a missing record → resolves to null (no findById on a deleted id → no 500).
store — before
edges: [ →abc, →def ]
InventoryItem:abc{…}
→
after modify + evict + gc
edges: [ →abc, →def ]
InventoryItem:abc{…}

read  Opening detail — why it never hits the network

  1. Feed already cached the entity (same fragment) as InventoryItem:{id}.
  2. Detail uses useQuery(INVENTORY_ITEM_QUERY, { fetchPolicy: 'cache-only' }) — it is forbidden from going to the network.
  3. The inventoryItem read redirect resolves the query to the cached InventoryItem:{id} → renders instantly.
  4. After a delete, that reference dangles → returns null → the screen shows "no item" gracefully instead of refetching a deleted row.

cache-only + the redirect are a pair: the redirect populates the field from the feed's entity; cache-only stops a post-delete refetch storm.

When you SHOULD refetch instead: if sorting/filtering changes which rows belong (or their order), or a server-computed field changes that you can't reproduce on the client. Cache surgery is for membership you can compute locally (add/remove/edit a known row); a refetch is correct when the server decides membership.
