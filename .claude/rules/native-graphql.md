# Native GraphQL (Apollo + codegen client-preset)

The RN apps talk to core-server over GraphQL (Apollo Client v4). Operations are **typed documents**
generated by graphql-codegen `client-preset` from core-server's code-first schema. The Apollo client +
cache live in the host (`core-app`); micro-apps consume the host's shared client.

## Codegen — typed documents from the schema

> WHY: the schema (`apps/core-server/src/schema.gql`, regenerated by NestJS) is the source of truth.
> `client-preset` gives every operation a `TypedDocumentNode`, so `useQuery`/`useMutation` infer
> variables + results — no hand-written response types, no `as` casts.

- Each app has a `codegen.ts` (`preset: 'client'`, `schema: '…/core-server/src/schema.gql'`,
  `documents: ['src/**/*.{ts,tsx}']`, `presetConfig: { fragmentMasking: false }`,
  `config: { scalars: { DateTime: 'string' } }`) + a `codegen` script.
- Output goes to `src/gql/` and is **git-ignored** — run `pnpm codegen` before typecheck/dev (it also
  validates every operation against the schema). Re-run it whenever you add/change an operation.

## Structure — layer-first, fragment-first

GraphQL operations, hooks, and zod schemas are **top-level `src/<layer>/<domain>/` folders** (not
colocated inside the feature). A feature folder holds UI only — the navigator + screens, `components/`,
`forms/`, and its UI config.

```
src/
├── gql/                          # codegen output — git-ignored
├── graphql/<domain>/             # operations (this layer)
│   ├── fragments.ts    # graphql(`fragment XFields on X { … }`)
│   ├── queries.ts      # graphql(`query …`)
│   ├── mutations.ts    # graphql(`mutation …`)
│   └── index.ts        # barrel
├── hooks/<domain>/               # typed hooks + index.ts barrel
├── services/<domain>/            # non-React data/helpers (axios, option lists) + index.ts barrel
├── schemas/<domain>/             # zod schemas + inferred types
├── types/                        # shared hand types (enum unions — see caveat)
└── features/<domain>/            # UI only
    ├── index.tsx                 # navigator + screens
    └── components/  forms/       # screen-local UI
```

- Define documents with `graphql(\`…\`)` imported from `src/gql` — **never** `gql` from `@apollo/client`.
- Define a shared fragment per entity and reference it by name (`...XFields`) in operations; client-preset
  links named fragments across files and bundles them into the runtime document. Reuse the SAME fragment in
  the list query, single-item query, and create/update mutations so cached records are identical and
  identity-merge (by `id`) keeps list/detail/edit in sync.

> **core-app exception:** core-app uses these same layers but **prefixed under `src/host/`**
> (`src/host/graphql/<domain>/`, `src/host/hooks/<domain>/`, …). Its auth/account operations are currently
> authored as raw `gql` from `@apollo/client` with hand-typed result interfaces (only `graphql/generated/`
> codegen types are used, for inputs); migrating them to typed `graphql()` documents is a pending follow-up.
> Per-domain barrels exist for `graphql/`, `hooks/`, and `services/`; **schemas and routes are imported by
> file** (no per-domain barrel) — see `native-screen.md`.

```ts
// src/graphql/inventory-items/fragments.ts
import { graphql } from '../../gql';
export const InventoryItemFieldsFragment = graphql(`fragment InventoryItemFields on InventoryItem { id name … }`);
// src/graphql/inventory-items/queries.ts
export const INVENTORY_ITEM_QUERY = graphql(`query InventoryItem($id: ID!) { inventoryItem(id: $id) { ...InventoryItemFields } }`);
```

## Hooks — infer from the typed document

```ts
// CORRECT — useMutation infers data/variables from the typed doc; no casts.
const [createItem] = useMutation(CREATE_INVENTORY_ITEM, {
  update(cache, { data }) { const created = data?.createInventoryItem; /* typed */ },
});
// WRONG — manual response typing / casts:
const created = (data as { createInventoryItem?: {…} })?.createInventoryItem;
```

- `useQuery(DOC)` / `useMutation(DOC)` with a typed document — let them infer; don't pass explicit
  `<TData>` generics unless deliberately substituting a more precise hand type (see enum caveat).
- The generic `useApolloInfiniteList` (quantum) accepts a typed document (it satisfies the `DocumentNode`
  branch) plus an explicit node type `T`; the document still gets codegen-validated.
- **One hook per file, file named exactly after the hook** — `useCreateInventoryItem.ts` exports
  `useCreateInventoryItem` and nothing else. NEVER bundle several hooks in one file (no
  `useInventoryItemMutations.ts` holding create/update/delete). The domain barrel
  (`src/hooks/<domain>/index.ts`) re-exports every hook; consumers import from the barrel
  (`../../hooks/<domain>`), never the individual files.

```
src/hooks/inventory-items/
├── index.ts                      # barrel — export * from each hook file
├── useInventoryItemsFeed.ts      # one hook
├── useCreateInventoryItem.ts     # one hook
├── useUpdateInventoryItem.ts     # one hook
└── useDeleteInventoryItem.ts     # one hook
```

## List loading — pass `loading` straight to `FlashList isLoading`

A `screenScroll` list screen wires the query's `loading` **directly** to `<FlashList isLoading={…}>`. Do NOT
gate it on `data.length === 0` (`loading && networkStatus === NetworkStatus.loading && items.length === 0`).

```tsx
// WRONG — skips the skeleton whenever cached data is present
const isInitialLoading = loading && networkStatus === NetworkStatus.loading && items.length === 0;
<FlashList screenScroll isLoading={isInitialLoading} data={items} … />

// CORRECT — loading straight through
const { data, previousData, loading } = useThings(search);
const items = (data ?? previousData)?.things ?? [];
<FlashList screenScroll isLoading={loading} data={items} … />
```

WHY: with `cache-and-network` + `notifyOnNetworkStatusChange`, `loading` is true whenever a fetch is in flight —
first load, a cached re-mount's revalidation, and a search refetch — so `<FlashList>` shows its skeleton on each.
That skeleton pass is **deliberate**: it lets the transparent `<ScreenHeader>` register its content inset BEFORE
the real list lays out. The old `… && items.length === 0` guard skipped the skeleton when cached data existed, so
on a cached re-entry the real list rendered on the first pass and seated UNDER the header (first card clipped
beneath the search bar) — the bug on "More"-menu list screens on second entry. A relay feed via
`useApolloInfiniteQuery` already returns `isLoading` this way (`networkStatus === loading`, no data guard), so it
was immune; plain-query list screens must match it. Trading a brief skeleton on refetch for correct header
seating is intended.

## Enum caveat

Server `InventoryItem.type`/`tracking`/`pickStrategy` are GraphQL `String` (mirroring the DTOs), so the
generated types are `string`. Where enum precision matters (forms, `useQuery<…>` on detail/edit), pass an
explicit hand type whose enums are unions (kept in `src/types/`). Fixing this properly = making those
server fields GraphQL enums (then drop the hand types).

## Cache policies — each micro-app registers its own

The generic Apollo layer lives in `@vritti/quantum-ui-native/apollo`: the host builds the one client +
persisted `InMemoryCache` via `createApolloClient(...)` in `core-app/src/host/config/apollo.ts` and takes
NO micro-app schema. Each micro-app registers its own entity policies at runtime:

```ts
// top of the MF-exposed feature entry (e.g. features/inventory-items/index.tsx) — module-eval scope
import { registerConnection } from '@vritti/quantum-ui-native/apollo';
registerConnection({ field: 'inventoryItems', keyArgs: ['filters', 'search', 'sort'], singleField: 'inventoryItem', typename: 'InventoryItem' });
```

`registerConnection` adds `relayStylePagination` on the feed field + a by-id `read` redirect for the
single-item field (via `cache.policies.addTypePolicies`). Call it at the feature module's TOP-LEVEL (it
runs once on the host's lazy import, before any screen here mounts/queries) — NEVER in a hook/effect,
which runs after the first render and misses the page-1 relay merge. For a bare field use
`registerTypePolicies(policies)`.

## Also applies
- `export function useX()` (not const); hooks in `src/hooks/<domain>/` with a barrel; one domain owns its operations (`src/graphql/<domain>/`).
- Mutations keep the cache live with surgery — use the generic helpers from `@vritti/quantum-ui-native/apollo`:
  `prependEdgeToConnection` (create), `removeEdgeFromConnection` + `evictEntity` (delete); update is identity
  auto-merge by id (no surgery). Never blanket refetch. See [[project_apollo_infinite_list_hook]] equivalents.
